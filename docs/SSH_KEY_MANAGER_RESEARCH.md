# Исследование: менеджер SSH-ключей (по мотивам Purple)

**Дата:** 2026-10-19
**Источник:** репозиторий [erickochen/purple](https://github.com/erickochen/purple) v3.30.0 (MIT), разбор кода `src/ssh_keys.rs`, `src/key_push.rs`, `src/key_activity.rs`, `src/askpass*.rs`, `src/ssh_config/`; текущая реализация SSH в DevConsole Hub.
**Вопрос:** нужен ли в приложении менеджер SSH-ключей, и в каком объёме. Исходная боль — один ключ на все серверы.

> **Решение владельца (2026-10-19):** делаем только локальный менеджмент и отображение проблем, без подключения к серверам. Реализовано как раздел «SSH-ключи» — `docs/PLAN.md`, этап 28. Шаги 2–3 ниже (раскатка и ротация на серверах) не делаем.

---

## TL;DR

1. **Purple целиком встраивать не нужно и нельзя:** это отдельный TUI (ratatui) на 220 тыс. строк Rust, у которого источник истины — `~/.ssh/config`, а у нас — SQLCipher-база. Половина его ценности (синхронизация с 18 облаками, туннели, Docker/Podman, MCP-сервер, Vault) к ключам не относится. Лицензия MIT — идеи и отдельные фрагменты переносить можно.
2. **Ключевая часть Purple узкая:** инвентаризация `~/.ssh/*.pub` (тип, отпечаток, randomart, оценка стойкости, зашифрован ли, загружен ли в агент, какие хосты используют) + раскатка публичного ключа на N хостов. **Генерации ключей и ротации (удаления старого ключа с серверов) в Purple нет.**
3. **«Один ключ на все серверы» — не главная проблема.** Сервер никогда не получает приватный ключ, поэтому взлом одного сервера не раскрывает ключ от остальных. Реальные риски — в другом: ключ без passphrase на ноутбуке, нет списка «где этот ключ установлен» (а значит, нет быстрого отзыва), устаревший RSA-2048, проброс агента. Разумная схема — **ключ на зону доверия** (личные / работа / клиент X / прод / deploy), а не на каждый сервер.
4. **Рекомендация — делать, но своё и узкое:** раздел «SSH-ключи» поверх нашей модели консолей, в три шага: инвентаризация с предупреждениями → создание и раскатка ключа → мастер ротации (то, чего нет в Purple и что закрывает исходную боль). Оценка — 1–2 дня на первый шаг, ~1 неделя на всё.

## 1. Что такое Purple

| | |
|---|---|
| Что это | Терминальный (TUI) SSH-менеджер и редактор `~/.ssh/config`, один бинарник |
| Стек | Rust 2024, `ratatui` + `crossterm`, `ureq`, внешние `ssh` / `ssh-keygen` / `ssh-add` |
| Объём | ~222 тыс. строк Rust, из них большая часть — тесты (6700+) |
| Хранилище | Нет БД: правит `~/.ssh/config` с сохранением комментариев, отступов, `Include`. Своё состояние — `~/.purple/*.json` |
| Лицензия | MIT |

Возможности:

- **Синхронизация с облаками** (AWS, GCP, Azure, Hetzner, DO, Proxmox, Teleport, NetBox и др.): по API-токену новые VM появляются в `~/.ssh/config`, удалённые помечаются устаревшими.
- **Поиск по хостам** (`:`), детальная панель хоста: статус, маршрут ProxyJump, активность за год, теги.
- **Docker/Podman по SSH** на всех хостах, без агента на сервере.
- **Мониторинг туннелей** (Local/Remote/Dynamic forward) с трафиком по процессам.
- **Сниппеты** — команда на группу хостов с «радиусом поражения» и историей запусков.
- **Ключи** — см. ниже.
- **Пароли** из Keychain, 1Password, Bitwarden, pass, Vault KV, Proton Pass (через `SSH_ASKPASS`, как у нас).
- **Vault SSH-сертификаты** — короткоживущие подписанные сертификаты с полосой TTL.
- Файловый менеджер (scp), MCP-сервер для AI-агентов.

## 2. Как устроен модуль ключей Purple

### 2.1 Инвентаризация (`ssh_keys.rs`)

- Сканирует `~/.ssh/*.pub` (кроме `authorized_keys.pub`, `known_hosts.pub`), следует симлинкам.
- По каждому ключу: имя, тип и длина, SHA256-отпечаток, комментарий, randomart (свой порт алгоритма Drunken Bishop из OpenSSH `sshkey.c`), признак сертификата (`-cert.pub`), mtime.
- **Зашифрован ли приватный ключ** — сначала по заголовку файла в процессе (`ssh_keys/native.rs`), иначе `ssh-keygen -y -P "" -f <key>`: успех = без passphrase.
- **Загружен ли в агент** — один вызов `ssh-add -l`, сравнение отпечатков.
- **Связанные хосты** — какие `Host` в `~/.ssh/config` ссылаются на ключ через `IdentityFile`.
- **Оценка стойкости 0–100:** `sk-*` (аппаратный) 95, ED25519 90, ECDSA 70–85, RSA ≥4096 80 / 3072 75 / 2048 55 / <2048 ≤15, DSA 5; плюс 5 за passphrase, минус 10 без неё.

### 2.2 Раскатка ключа (`key_push.rs`)

- Аналог `ssh-copy-id` на много хостов параллельно, по `p` на выбранном ключе.
- Команда: `ssh -F <config> -T -o ConnectTimeout=10 -o ServerAliveInterval=10 -o ServerAliveCountMax=3 -o ControlMaster=no -o StrictHostKeyChecking=yes|accept-new [-o BatchMode=yes] -- <alias> '<snippet>'`, публичный ключ — через stdin (без экранирования в командной строке).
- Удалённый сниппет идемпотентен: создаёт `~/.ssh` (700) и `authorized_keys` (600) только если их нет, нормализует CRLF, проверяет дубликат `grep -qxF`, дописывает, на последней строке печатает маркер `__PURPLE_KEY_PUSH:APPENDED__` / `ALREADY_PRESENT__` / `APPEND_FAILED__` (маркер, а не код возврата — чтобы motd/баннер не ломал разбор).
- Неизвестный ключ хоста → отдельный диалог доверия и повтор с `accept-new`. Пароль сервера — через askpass. Хосты под Vault-сертификатами пропускаются.
- ssh запускается в своей группе процессов — отмена убивает и `ProxyCommand`.

### 2.3 Активность (`key_activity.rs`)

Журнал `(alias, timestamp)` каждого подключения в `~/.purple/key_activity.json`; на вкладке ключей превращается в «последнее использование» и спарклайн через связку ключ → хосты.

### 2.4 Чего в Purple нет

- Генерации ключей (`ssh-keygen -t ...`) из интерфейса.
- **Ротации:** удаления ключа из `authorized_keys`, замены старого ключа новым на группе хостов, проверки входа новым ключом.
- Аудита `authorized_keys` на серверах (какие ещё ключи туда пускают).

## 3. Как SSH устроен у нас сейчас

- Консоль `connection_type = "ssh"` хранит в `consoles`: `ssh_host`, `ssh_port`, `ssh_user`, `ssh_key_path`, `ssh_extra_args`, `ssh_passphrase`, `ssh_password` (всё в SQLCipher).
- Команду собирает `buildSshCommand()` (`src/lib/connectionString.ts`): `ssh -o StrictHostKeyChecking=accept-new [-p] [-i "<key>"] [extra] user@host`.
- `pty_manager.rs`: при passphrase — `ssh-add` через временный askpass-скрипт; при пароле сервера — askpass-скрипт в `/tmp` (известная проблема, PLAN.md 19.4).
- `~/.ssh/config` мы не читаем и не пишем. Ключ — просто путь к файлу, выбранный в диалоге консоли; список ключей, их состояние и «где используется» нигде не видно.

Следствия:

- **Нет `IdentitiesOnly=yes` при заданном `-i`.** ssh всё равно предлагает серверу все ключи из агента и дефолтные `id_*`. При 5–6 ключах в агенте получаем `Too many authentication failures` — как только пользователь заведёт отдельные ключи, это всплывёт сразу. Плюс сервер видит все ваши публичные ключи.
- Консоли без `ssh_key_path` молча ходят дефолтными ключами — из интерфейса не понять, каким именно.
- Passphrase у нас уже хранится в зашифрованной БД и подставляется сама — то есть **ключ с passphrase у нас не менее удобен, чем без неё**. Это сильный аргумент в пользу встроенного менеджера: он может сделать безопасный вариант вариантом по умолчанию.

## 4. Один ключ на все серверы — это неправильно?

### Чего бояться не нужно

При аутентификации по ключу сервер получает только публичный ключ и подпись. **Взломанный сервер не может «украсть» ваш ключ** и пойти с ним на другие серверы. Поэтому «ключ на каждый сервер» почти не повышает защиту, а управлять 40 ключами тяжело.

### Реальные риски

| Риск | Почему опасно | Что помогает |
|---|---|---|
| Приватный ключ **без passphrase** | Украденный ноутбук, бэкап, вредонос, синхронизация `~/.ssh` в облако — сразу доступ ко всем серверам | Passphrase (у нас — хранится в БД и подставляется сама; на macOS ещё `UseKeychain yes`); аппаратный ключ (`sk-ed25519` / Secure Enclave) |
| **Нет списка, где ключ установлен** | При утечке непонятно, откуда его удалять; в итоге не удаляют нигде | Инвентаризация «ключ → консоли» + мастер ротации |
| Слабый алгоритм | DSA — сломан, RSA-1024 — небезопасен, RSA-2048 — пока допустим, но устаревает | ED25519 |
| **Проброс агента** (`ForwardAgent yes`) на общий сервер | root на этом сервере может пользоваться вашим агентом, пока вы подключены | Не пробрасывать агент; для прыжков — `ProxyJump` |
| Один ключ и для личного, и для клиентских/рабочих серверов | При увольнении/окончании контракта нельзя «отдать» доступ отдельно; ключ из одной зоны открывает другую | **Ключ на зону доверия** |
| Deploy-ключ (CI, GitHub) совпадает с личным | Утечка из CI = доступ к вашим серверам | Отдельный ключ без доступа к интерактивным серверам |

### Рекомендуемая схема

- **Ключ на зону доверия, не на сервер:** `personal`, `work`, `client-<имя>`, `prod` (если прод критичен), `deploy` / `github`. На практике — 3–6 ключей.
- Все ключи — ED25519, **с passphrase**; где возможно — аппаратные.
- Плановая ротация не обязательна (ключ не «стареет» сам), но **ротация по событию** (утечка, смена ноутбука, конец проекта) должна делаться за минуты, а не за вечер ручной работы. Именно это и стоит автоматизировать.

## 5. Варианты для DevConsole Hub

### A. Встроить / запускать Purple
❌ Отдельный TUI со своим источником истины (`~/.ssh/config`), наше дерево консолей он не знает. Встроить можно только как программу во вкладке терминала — пользователь это может сделать и сам (`brew install`).

### Б. Синхронизация с облаками, туннели, контейнеры
⏸ Отдельные большие темы, к ключам отношения не имеют. Не сейчас. Если понадобится — Docker по SSH и импорт серверов из Hetzner/DO хорошо ложатся на наши быстрые команды и дерево.

### В. Свой узкий менеджер ключей — рекомендуется

**Шаг 1. Инвентаризация и предупреждения** (~1–2 дня, без записи на серверы)
- Новый раздел «SSH-ключи» (окно из настроек или пункт в меню дерева).
- Rust-команда `list_ssh_keys`: скан `~/.ssh/*.pub`, `ssh-keygen -l -E sha256`, проверка шифрования, `ssh-add -l` — по образцу Purple.
- Для каждого ключа — **какие консоли его используют** (по `ssh_key_path`, это мы знаем точно, без `~/.ssh/config`), плюс отдельная строка «консоли без ключа (дефолтные `id_*`)».
- Оценка стойкости и понятные предупреждения: «без passphrase», «RSA 2048», «используется N консолями из разных воркспейсов».
- Попутно: `-o IdentitiesOnly=yes` в `buildSshCommand()`, когда задан ключ.

**Шаг 2. Создание и раскатка** (~2–3 дня)
- «Создать ключ»: ED25519, имя, комментарий, passphrase (по умолчанию — сгенерированная и сохранённая в БД). Генерация в процессе через крейт `ssh-key` (RustCrypto) — чтобы passphrase не попадала в argv `ssh-keygen -N`, видимый в `ps`.
- «Установить на серверы»: выбор консолей в дереве (воркспейс/проект целиком), идемпотентный сниппет как у Purple, вход текущими реквизитами консоли (ключ/пароль). Итог по каждой консоли: добавлен / уже был / ошибка.
- После успешной установки — предложить переключить `ssh_key_path` консоли на новый ключ.

**Шаг 3. Мастер ротации** (~3–4 дня) — то, чего нет в Purple
1. Выбрать старый ключ → список консолей, которые его используют.
2. Создать новый ключ (шаг 2) или выбрать существующий.
3. Для каждой консоли: установить новый ключ → **проверить вход новым ключом** (`ssh -o IdentitiesOnly=yes -o BatchMode=yes -i new ... true`) → переключить консоль на новый ключ → удалить старый из `authorized_keys` (бэкап `authorized_keys.bak-<дата>`, `grep -vxF`).
4. Старый ключ удаляется со сервера **только после успешной проверки** нового на этом же сервере. Ошибка на любом шаге — консоль остаётся на старом ключе, в отчёте причина.
5. В конце — предложить удалить или убрать в архив старый приватный ключ локально.

**Позже, по желанию**
- Импорт хостов из `~/.ssh/config` в дерево (разовый, с выбором) — у многих пользователей серверы уже описаны там.
- Аудит `authorized_keys` на сервере: какие ключи туда пускают, с подсветкой «наши» / «неизвестные».
- Ключи в Secure Enclave (macOS) / FIDO2 (`sk-ed25519`).
- Журнал «последнее подключение этим ключом» — у нас уже есть статистика использования (этап 21), связка ключ → консоли даёт это почти бесплатно.

## 6. Риски реализации

- **Можно потерять доступ к серверу** при ротации. Защита: удалять старый ключ только после проверки нового на том же сервере, бэкап `authorized_keys`, не трогать серверы без проверки, режим «только показать, что будет сделано».
- **Разные окружения на сервере:** `AuthorizedKeysFile` в нестандартном месте, ключи под управлением Ansible/Puppet (перезапишут), FreeIPA/LDAP, Windows OpenSSH. Сниппет должен честно сообщать «не нашёл / не смог», а не делать вид, что получилось.
- **Секреты:** пароли серверов при раскатке идут через askpass — сначала стоит закрыть пункт про askpass-файлы в `/tmp` (PLAN.md 19.4), иначе новая фича умножит старую проблему.
- **Host key:** для раскатки — та же политика, что у консолей (`accept-new`), неизвестный ключ хоста показывать пользователю.
- Экспорт `.dchub` уже переносит `ssh_key_path` и passphrase, но не сам файл ключа. Переносить приватные ключи в экспорте — отдельное решение (скорее нет, или только по явной галочке).

## 7. Вывод

Делать имеет смысл: SSH-консоли — основной сценарий приложения, а passphrase и пароли уже лежат в зашифрованной БД, так что встроенный менеджер может сделать безопасную схему (несколько ED25519-ключей с passphrase по зонам) не менее удобной, чем нынешнюю «один ключ без пароля». Брать у Purple стоит идеи инвентаризации, оценки стойкости и идемпотентного сниппета раскатки; облачную синхронизацию, туннели и контейнеры — нет. Главная ценность для нас — мастер ротации, которого в Purple нет.
