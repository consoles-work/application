# Rust + TS: линейно читаемый код

Сделан по мотивам `ts-readable-flow` и адаптирован под этот проект: Tauri, бэкенд на Rust (`src-tauri/src/*.rs`) и фронт на React + TS (`src/lib`, `src/stores`, `src/components`). Общие правила одинаковы для обоих языков. Различия — в разделах «Rust», «React / TS» и «Граница Rust ↔ TS».

## Цель

Чтобы понять, **что** делает файл, функция или компонент, не нужно открывать другую функцию или файл. Открывать функцию стоит, только чтобы узнать, **как** устроена деталь.

Главная метрика — сколько фактов читателю приходится держать в голове одновременно (cognitive load). Число строк вторично: 50 строк линейного кода читаются легче, чем 6 функций по 10 строк, которые нельзя понять друг без друга.

## Общие правила

### 1. Шапка файла — смысл процесса по шагам, без пересказа реализации

Файл, который реализует процесс (PTY-сессия, экспорт/импорт, скан SSH-ключей, терминал во вкладке, аудит), открывается комментарием. В нём сказано, **что это за процесс, для кого он, по каким шагам идёт и чем заканчивается каждый шаг**. Комментарий пишется для того, кто хочет понять модуль без чтения кода, поэтому язык — предметной области, а не реализации:

- одна фраза: что делает модуль и кто его вызывает (какая панель или действие пользователя, какая сторона IPC);
- для каждой публичной операции — **пронумерованные шаги**: что проверяется, что происходит, какие **исходы** (`а) / б) / в)`) и что каждый из них значит для вызывающего (что увидит пользователь, можно ли повторить);
- **почему** так сделано — только у неочевидных решений (ограничение WebKit или ОС, инцидент, требование безопасности);
- общие правила процесса (что считается ошибкой, что делается «по возможности» и молча) — в конце.

Формат — как уже принято в проекте: рамка `// ═══` с именем файла и назначением, под ней текст шапки. В Rust и в TS одинаково.

Техническая реализация видна из кода, поэтому в шапке её **не дублируют**: имена Tauri-команд и событий, ключи настроек (`ui.theme`), SQL, regex, пути к временным файлам, тексты ошибок, значения констант (таймауты, размеры буферов), имена вызываемых функций и порядок вызовов. Оставить можно то, чего в коде **не видно**, но что нужно для понимания контракта: поведение ОС («приложение, запущенное из Dock, не наследует локаль»), чего ждёт другая сторона IPC («фронт по выходу процесса показывает “сессия завершена”»), смысл форматов внешних программ (`ssh-add -l`, `~/.ssh/config`).

Проверка: если строку шапки можно восстановить, прочитав одну строку кода, она лишняя. Шапка обычно занимает 5–15 строк. У фасадов (`commands.rs`, `tauriCommands.ts`) и pass-through слоёв — 1–3 строки о назначении.

Блок «Rust-новичкам» в `commands.rs` и `db.rs` — справка по языку, а не шапка процесса, и описания процесса не заменяет. Удалять его можно только с согласия владельца.

```rust
// ══════════════════════════════════════════════════════════════════
// pty_manager.rs — терминальные сессии консолей
// ══════════════════════════════════════════════════════════════════
//
// Держит живые терминалы; вызывается вкладками терминала через IPC.
//
// spawn — открыть терминал консоли:
//  1. Ключ с passphrase кладём в ssh-agent заранее — иначе ssh спросит
//     passphrase прямо в терминале.
//  2. Запускаем шелл консоли или шелл ОС по умолчанию. Команда с аргументами
//     (`ssh user@host`) идёт через `sh -c`.
//  3. Окружение: UTF-8-локаль и тип терминала, если консоль их не задала, —
//     приложение из Dock локаль не наследует, и кириллица ломается.
//     Переменные консоли — поверх.
//  4. Пароль сервера ssh получает не из терминала, а через askpass.
//  5. Вывод пересылается на фронт фоновым потоком; многобайтовый символ на
//     границе чтения не режется. Процесс завершился — сессия удаляется,
//     фронт получает событие о выходе.
//  Исход: а) id сессии; б) PTY не открылся или шелл не запустился —
//  ошибка, фронт печатает её в терминале красным.
//
// write / resize / kill — по id сессии; сессии нет — ошибка, фронт её глотает
// (вкладка уже закрывается).
```

```tsx
// ══════════════════════════════════════
// TerminalView — один терминал консоли во вкладке
// ══════════════════════════════════════
// Открытие вкладки:
//  1. Создаём xterm с настройками и темой пользователя.
//  2. Решаем, что запускать: локальный шелл в папке проекта или SSH-команду —
//     ту же, что копирует кнопка «Копировать» в диалоге консоли.
//  3. Запускаем сессию в бэкенде. Не запустилась — ошибка красным в самом
//     терминале. Вкладку закрыли раньше, чем сессия поднялась, — сразу убиваем.
//  4. Стартовые команды консоли — по строке с паузой, чтобы шелл успел подняться.
// Закрытие вкладки — сессия убивается, xterm освобождается.
```

Шапка и код — одно целое:

- абзацы кода начинаются с **тех же номеров**: `// 3. Окружение.`;
- doc-комментарий вспомогательной функции говорит, **какой шаг** она реализует: `/// Шаг 4: …` (Rust), `/** Шаг 4: … */` (TS);
- у констант — к какому шагу они относятся: `/// Шаг 5: размер буфера чтения PTY.`;
- поведение изменилось — шапка правится **в том же изменении**.

`docs/ARCHITECTURE.md`, `CLAUDE.md` и README шапку не заменяют: читатель кода их не откроет.

### 2. Сценарий — одна функция, сверху вниз

Публичная операция пишется одной функцией из **абзацев**: пустая строка, затем комментарий-заголовок с номером шага из шапки. В Rust это `pub fn` модуля. В TS — обработчик события, тело `useEffect` или action стора. Примеры ниже показывают раскладку; имена в них условные, это не текущий код.

```rust
pub fn spawn(cfg: SpawnConfig) -> Result<u32, String> {
    // 1. Ключ с passphrase — в ssh-agent заранее.
    if !cfg.ssh_passphrase.is_empty() {
        add_key_to_agent(&cfg.ssh_key_path, &cfg.ssh_passphrase);
    }

    // 2. PTY и команда консоли.
    let pair = native_pty_system().openpty(INITIAL_SIZE).map_err(|e| e.to_string())?;

    let mut cmd = shell_command(&cfg.shell);

    if !cfg.cwd.is_empty() {
        cmd.cwd(&cfg.cwd);
    }

    // 3. Окружение.
    …
}
```

```ts
const runQuickCommand = async (cmd: QuickCommand) => {

  const ptyId = ptyIdRef.current;

  …

```

### 3. Один процесс — один файл, пока он читается

Не делить процесс на слои заранее. Разделение оправдано, когда часть реально переиспользуется или файл перестал читаться целиком. Иначе читатель прыгает между файлами, а между ними появляются посредники и типы-переходники.

Процесс, который пересекает IPC, неизбежно живёт в нескольких местах: Rust-модуль (действие), обёртка в `tauriCommands.ts`, компонент или `src/lib` (сценарий интерфейса). Это граница, а не слой. Новых посредников вокруг неё не добавлять: «сервис» поверх `tauriCommands.ts`, «менеджер» поверх стора, Rust-модуль между `commands.rs` и `db.rs`.

### 4. Выделять функцию — только в трёх случаях

1. **Переиспользуется** (вызывается из ≥ 2 мест).
2. **Глубокая функция**: законченный шаг, который полностью описывают имя, сигнатура и строка «Шаг N: …», а реализация намного сложнее интерфейса (`drain_utf8(pending) -> String`, `buildSshCommand(console)`, хук `useTabReorder(onDrop)`).
3. **Техническая деталь**, в которую читателю сценария заглядывать не нужно (`ssh_string`, `display_path`, `file_mode` с вариантами под `cfg`).

Шаг, который вызывается **один раз** и без которого сценарий непонятен, — **не выделять**, оставить абзацем. Однострочные обёртки с одним вызовом — встроить.

### 5. Глубина чтения — не больше одного уровня

Сценарий → глубокие функции и детали. Не сценарий → шаг → подшаг → подподшаг.

### 6. Плоский поток

- Guard clauses и ранний `return` вместо лесенки `if/else` (как это делается в Rust и TS — в разделах ниже).
- Вложенность управляющих конструкций — не глубже 2.
- Нет переменных, которые переприсваиваются через всю функцию (`let mut` в Rust, `let` в TS). Исход шага — значение (`Result`/`Option`/`enum` в Rust, `T | Error` или размеченное объединение в TS), а не набор флагов.
- Ветвление выражением, а не присваиванием в ветках: `let x = match …`, `const x = cond ? a : b` — но без вложенных тернарников.

### 7. Пустые строки — после каждого оператора

Внутри тела функции, хука и обработчика **после каждого оператора ставится пустая строка**, в том числе:

- между переменной и однострочной проверкой этой переменной;
- между соседними однострочными `if … return` (даже если вместе они — таблица решений);
- между `let x;` и следующим за ним `try {` (TS);
- между изменением состояния и логом, логом и `return` / хвостовым выражением.

**Единственное исключение** — несколько подряд идущих **однотипных** операторов, которые читаются как одна таблица: объявления переменных и констант, присваивания настроек, регистрации одного вида (`cmd.env(...)`, `term.loadAddon(...)`, `window.addEventListener(...)`). Они идут одним блоком, а первый оператор другого вида после блока — через пустую строку.

На JSX-разметку, на `match`-рукава и на поля структур правило не распространяется. `rustfmt` пустые строки не удаляет (сжимает только подряд идущие).

```rust
let sessions = get_sessions();
let mut map = sessions.lock().map_err(|e| e.to_string())?;

let Some(session) = map.get_mut(&pty_id) else {
    return Err(format!("PTY session {} not found", pty_id));
};

session.writer.write_all(data.as_bytes()).map_err(|e| e.to_string())
```

### 8. Решения отдельно от действий

Ветвление **по данным** (тип ключа → длина, статус → цвет, тип подключения → что запускать) выносится в чистую функцию или таблицу. В сценарии остаётся цепочка «вызвали → решили → вызвали» (functional core / imperative shell).

- Rust: чистая `fn` с `match` (`type_and_bits`, `default_shell`) или `const`-таблица (`const X: &[(&str, …)]`).
- TS: чистые функции в `src/lib/*.ts` без React и `invoke` (`sshAudit.ts`, `quickCommandStats.ts`, `links.ts`) или `Record<…>`-таблица. Компонент — оболочка: прочитал стор → вызвал чистую функцию → отрисовал или вызвал команду.

Чистая функция — то, что можно проверить тестом. В Rust для этого есть `#[cfg(test)] mod tests` (примеры — `security.rs`, `ssh_keys.rs`). В TS тестового раннера в проекте нет.

### 9. Сначала убрать лишнюю сложность, потом раскладывать

Раскладка не спасает от лишнего кода. До того как браться за структуру, удалить:

- мёртвые ветки (флаг, зашитый константой) — понадобятся, вернём из git;
- особые случаи, которые почти ничего не меняют (код ниже и так даст тот же результат);
- дубли: одинаковые проверки, повторяющиеся строки, одинаковый код в двух функциях (например, запись askpass-скрипта в `add_key_to_agent` и в `spawn` — это одна деталь `write_askpass`);
- типы, исходы которых обрабатываются одинаково.

Каждое удаление, которое меняет поведение (текст ошибки, строка лога, порядок действий), **явно перечисляется** в отчёте владельцу. Если изменение видно пользователю — строка в `CHANGELOG.md`. Если меняется текст в интерфейсе — правятся все 5 файлов `src/locales/*.json`.

### 10. Комментарий — замысел, код — шаги

Комментарий объясняет **почему** и **какой это шаг**. Что делает строка — должно быть видно из кода. Неочевидные контракты (текст ошибки, который разбирает другая сторона; формула, повторённая на фронте и в бэкенде) комментируются там, где этот контракт создаётся.

В проекте много ценных «почему»: HTML5 DnD не работает в WebKit, xterm сам обрабатывает paste, `PRAGMA key` должен идти первым. **При переносе и встраивании кода такие комментарии едут вместе с ним**, а не теряются.

## Rust

**Ошибки.**
- На границе IPC — `Result<T, String>`, как во всём проекте: Tauri отдаёт ошибку фронту строкой. Чужую ошибку переводить в строку один раз, в месте возникновения: `.map_err(|e| e.to_string())?`.
- Свой `enum` ошибок заводить, только если вызывающий различает исходы (а не печатает текст).
- `unwrap()` / `expect()` — только для инвариантов (глобал из `OnceLock` инициализирован в `setup`), с сообщением, какой инвариант нарушен. В остальных случаях — `?`, `unwrap_or…`, `let … else`.
- `let _ = …` и `.ok()` молча проглатывают ошибку. Допустимо для действий «по возможности» (удалить временный файл, выставить права) — с комментарием, почему это безопасно.

**Плоский поток.**
- Guard clause: `let Some(x) = … else { return … };`, `if … { return …; }`. Вместо `if let Some(s) = … { …; Ok(()) } else { Err(…) }` — `let-else` и дальше прямой путь.
- Во вспомогательных функциях, которые возвращают `Option`, — `?` по `Option` (`ssh_string`, `read_small`), без вложенных `match`.
- Нет `let mut`, меняющегося в нескольких абзацах. Значение получается выражением (`let x = if … { } else { };`, `let x = match …`), а для поэтапных преобразований подходит shadowing (`let raw = raw.trim();`). `let mut` допустим для заполняемого объекта в пределах одного абзаца (`CommandBuilder`, накопитель `Vec`).
- Исход шага — `Result` / `Option` / `enum` с данными, а не `bool`-флаги плюс `Option`-поля «на случай».
- Итераторы: линейное преобразование — цепочкой (`filter/map/collect`). Ранний выход, побочные эффекты или несколько накопителей — `for`. Цепочка, в которой замыкания разрослись в блоки, — `for` или именованная функция.
- `Ok(0) => break, … Err(_) => break` — объединить рукава: `Ok(0) | Err(_) => break`.

**Блокировки.** Область `lock()` видна и минимальна: взяли, сделали операцию, отпустили. Не держать `Mutex` во время IO, запуска процесса или `emit` — вынести операцию под замком в блок `{ … }` или освободить через `drop`. `db.rs` берёт глобальное соединение сам, вызывающему держать его не нужно.

**Платформы.** `#[cfg(unix)]` / `#[cfg(target_os = …)]` — в деталь с вариантами под каждую платформу (как `file_mode` в `ssh_keys.rs`), а не вставками посреди сценария.

**Параметры.** Больше 4 параметров — это структура. Для Tauri-команды это `#[derive(Deserialize)] #[serde(rename_all = "camelCase")]` с полями, а фронт передаёт объект. Сигнатура команды — контракт IPC, поэтому такая правка делается в одном изменении с обёрткой в `tauriCommands.ts` и типом в `src/types/index.ts`.

**Логи.** `println!` — как в проекте: одна строка на событие (сессия запущена, БД пересоздана), а не после каждого вызова.

**Тесты.** `#[cfg(test)] mod tests` стоит последним в файле. Нетривиальная чистая функция, выделенная по п. 8, получает тест, если его ещё нет.

## React / TS

**Шапка компонента** (п. 1) описывает, что видит пользователь, и сценарии: действие пользователя или жизненный цикл → шаги → исходы.

**useEffect — это сценарий с жизненным циклом.**
- Один эффект — один ресурс или подписка, а её очистка в `return` стоит рядом с созданием.
- Большой эффект «создать xterm → подписаться → запустить PTY» — это один сценарий: абзацы с номерами внутри. Делить на несколько эффектов стоит, только если у частей разные зависимости, то есть разный жизненный цикл. Эффекты с одинаковыми зависимостями, разрезанные ради краткости, — conjoined.
- Производные данные вычисляются в рендере (или в `useMemo`, если это дорого), а не через `useState` + синхронизирующий `useEffect`.
- `// eslint-disable-line react-hooks/exhaustive-deps` — только с комментарием, почему зависимостей нет (эффект намеренно выполняется один раз при монтировании).

**Обработчики** (`handleX`, `onX`, `menuX`) — сценарии с абзацами: guard → команда → обновление стора → тост.

**Выделение (п. 4) в React.**
- Хук `useX` — глубокая функция, когда у него своё состояние, подписки и очистка (`useTabReorder`).
- Подкомпонент — когда у него своё состояние или он используется дважды (`QuickCommandsBar`, `DropMarker`).
- Кусок JSX, который используется один раз и не имеет своего состояния, в компонент ради «короче» не выносится.

**Ветвления в JSX.** Вложенные тернарники заменяются ранним `return` для состояний всего компонента (загрузка, пусто, ошибка), `&&` для одной ветки или таблицей `Record<состояние, …>`.

**Ошибки.** `.catch(() => {})` без комментария запрещён: ошибки десериализации IPC так пропадают молча (см. `CLAUDE.md`). Ошибку либо показать (`showToast` с типом `error`, красная строка в терминале), либо оставить комментарий, почему её можно игнорировать (`killPty` при размонтировании: сессия могла уже завершиться).

**Стор (zustand).** Изменение дерева, сессий и настроек — action в `appStore.ts`, один на операцию. Компонент не пересобирает `workspaces` сам. `useAppStore.getState()` внутри колбэков и эффектов — чтобы прочитать актуальное значение без подписки, это нормально.

**Модули `src/lib`.** Функции без React; `invoke` — только в `tauriCommands.ts`. На уровне модуля — объявления `function` (они поднимаются), стрелки — внутри компонентов для обработчиков.

**Тексты.** Только через `t()`. Новый ключ добавляется во все 5 локалей.

## Граница Rust ↔ TS

- Rust-структура с `#[serde(rename_all = "camelCase")]` и интерфейс в `src/types/index.ts` — зеркала. Поле добавляется и переименовывается в обоих в одном изменении, и обёртка в `tauriCommands.ts` проверяется.
- Логика, повторённая с двух сторон (разбор путей `expand_path` / `private_of` в `ssh_keys.rs` и в `sshAudit.ts`, формула сэкономленных символов в `record_quick_command_run` и в `TerminalPanel.tsx`), — комментарий в обоих местах со ссылкой на второе. Поменялась одна сторона — меняется и другая.
- Новая команда — по чеклисту из `CLAUDE.md` (регистрация — в `lib.rs`).

## Порядок в файле

Принцип — **наружу → внутрь**: сначала то, что видно снаружи, ниже — внутреннее. Переупорядочивание делается **отдельным шагом**, без правок логики, чтобы в диффе были видны только перемещения.

**Rust** (компилятору порядок безразличен):
1. Шапка.
2. `use`: `std` → внешние крейты → `crate::`.
3. `const`, затем `static` (глобальное состояние).
4. Типы: сначала `pub`, затем приватные.
5. `pub fn` — сценарии, в порядке процесса.
6. Приватные `fn` — детали, ниже сценариев; вызывающая выше вызываемой.
7. `#[cfg(test)] mod tests` — последним.

Секции отделяются рамками `// ══ Название ══`, как уже принято в проекте.

**TS-модуль** (`src/lib`, `src/stores`): импорты → типы (`export` выше) → константы → состояние модуля (не экспортируется) → `export function` → вспомогательные `function` в конце.

**Компонент** (`.tsx`): импорты → типы и константы → экспортируемый компонент → его подкомпоненты, хуки и хелперы ниже (объявлены через `function`, поэтому поднимаются).

## Красные флаги

- Шапки нет, или она — словарь терминов без шагов; номера шагов в коде не совпадают с шапкой.
- Шапка пересказывает реализацию: команды, события, ключи настроек, SQL, тексты ошибок, имена функций.
- **Conjoined functions** — две функции (или два эффекта) нельзя понять друг без друга, значит, это одна.
- **Pass-through** — функция только передаёт аргументы дальше. Исключение — публичные фасады: `#[tauri::command]` в `commands.rs` и обёртки в `tauriCommands.ts`.
- **Функция-шаг с одним вызовом**, которую приходится открывать, чтобы понять сценарий.
- **Тип ради одного перехода** между двумя функциями или файлами, который исчезает, если их слить.
- Процесс раскидан по нескольким файлам без переиспользования и без границы IPC.
- Переменная (`let mut` / `let`), меняющаяся в нескольких абзацах; набор флагов вместо исхода-значения; вложенность 3+; операторы без пустых строк между ними.
- Rust: `unwrap()` вне инварианта; `if let … else Err` вместо `let-else`; `Mutex` держится во время IO или `emit`; `#[cfg]`-вставки посреди сценария; одинаковый код в двух функциях.
- React: эффект без очистки подписки; `useState` + `useEffect` для производных данных; вложенный тернарник в JSX; `.catch(() => {})` без комментария; `exhaustive-deps` отключён без объяснения.

## Процедура рефакторинга

0. **Записать в `docs/PLAN.md`**, что рефакторим (`docs/RULES.md`, п. 1). Одно изменение — один процесс или файл; соседние файлы «заодно» не трогать.
1. **Описать процесс словами**: шаги, детали, исходы — как он работает сейчас. Если процесс нетривиальный, показать описание владельцу до переписывания.
2. **Снять метрики «до»** по файлу (раздел «Метрики»).
3. **One Pile**: собрать процесс в одном месте, встроить функции-шаги с одним вызовом и слои-посредники.
4. **Убрать лишнюю сложность** (п. 9), выписать изменения поведения.
5. **Шапка** из п. 1: смысл и исходы, без деталей реализации. Абзацы кода с номерами шагов, плоский поток (п. 6), пустые строки (п. 7).
6. **Выделить заново** только то, что проходит п. 4: глубокие функции (с «Шаг N:») и детали.
7. **Решения по данным** — в чистые функции или таблицы (п. 8); для нетривиальных Rust-функций — тест.
8. **Порядок в файле** — отдельным шагом, только перемещения.
9. **Проверка**:
   - `cd src-tauri && cargo check && cargo test`;
   - `npx tsc --noEmit`;
   - метрики «после» по тем же файлам;
   - правка затронула интерфейс — пройти сценарий в `npm run tauri dev` или попросить владельца.

   `cargo fmt` по крейту **не запускать**: `rustfmt.toml` в проекте нет, код отформатирован вручную (например, выровненные рукава `match`), и форматирование утопит рефакторинг в диффе. Prettier в проекте тоже нет.
10. **`docs/PLAN.md` и `docs/STATUS.md`** — отметить сделанное (`docs/RULES.md`). В `CHANGELOG.md` — только если изменилось поведение, видимое пользователю.

## Метрики

Нормы взяты из `ts-readable-flow`. Запуск — скриптами из папки скилла, из корня проекта. В проекте они ничего не меняют: пороги лежат здесь же (`clippy.toml`, `eslint.config.mjs`).

```bash
.claude/skills/readable-flow/rust-metrics.sh                       # весь крейт
.claude/skills/readable-flow/rust-metrics.sh src/pty_manager.rs    # только эти файлы
.claude/skills/readable-flow/ts-metrics.sh                         # весь src/
.claude/skills/readable-flow/ts-metrics.sh src/components/TerminalPanel.tsx
```

`ts-metrics.sh` при первом запуске ставит eslint с плагинами во временную папку (`$TMPDIR/readable-flow-eslint`, нужна сеть). Старый код замечаний даёт много, поэтому норма такая: **в отрефакторенных функциях замечаний ноль, в просто изменённых — не больше, чем было**.

**Пороговые:**

| Метрика | Порог | Rust (clippy) | TS (eslint) |
|---|---|---|---|
| Когнитивная сложность функции | ≤ 10 | `cognitive_complexity` | `sonarjs/cognitive-complexity` |
| Вложенность | ≤ 2 уровней управления | `excessive_nesting` = 4 — считает каждый блок, включая замыкания, `match` и его рукава | `max-depth` = 2 |
| Параметров | ≤ 4 | `too_many_arguments` | `max-params` (у компонента один объект props — норма) |

**Нулевые (наличие — нарушение):**

| Что | Rust | TS |
|---|---|---|
| `else` после ветки с `return` | `redundant_else` | `no-else-return` |
| Переприсваиваемая переменная | — (смотреть глазами `let mut`) | `prefer-const` |
| Вложенное условие, которое склеивается с внешним | `collapsible_if`, `collapsible_else_if` | `sonarjs/no-collapsible-if` |
| Булев шум | `needless_bool`, `nonminimal_bool` | `sonarjs/prefer-single-boolean-return`, `sonarjs/no-inverted-boolean-check` |
| Ветки и рукава с одинаковым телом, одинаковые функции | `if_same_then_else`, `match_same_arms` | `sonarjs/no-duplicated-branches`, `sonarjs/no-identical-functions` |
| Лишний `return` / `continue` | `needless_return` | `sonarjs/no-redundant-jump` |
| Переменная, сразу возвращаемая | `let_and_return` | `sonarjs/prefer-immediate-return` |
| Лесенка вместо guard clause | `manual_let_else`, `question_mark` | — |
| Вложенный тернарник | — | `no-nested-ternary` |
| Молча проглоченная ошибка | — (смотреть глазами `let _ =` / `.ok()`) | `.catch(() => {})` (`no-restricted-syntax`) |
| Хуки | — | `react-hooks/rules-of-hooks`, `react-hooks/exhaustive-deps` |

## Чек-лист

- [ ] Шапка файла: смысл процесса для вызывающего и шаги с исходами, без дублирования реализации (команды, события, ключи, SQL, тексты ошибок, имена функций, значения констант)
- [ ] Номера абзацев кода, «Шаг N:» у функций и констант совпадают с шапкой
- [ ] Что делает функция или компонент — понятно без открытия других функций и файлов
- [ ] Каждая выделенная функция, хук, подкомпонент: переиспользуется, или глубокая, или деталь
- [ ] Нет функций-шагов с одним вызовом, conjoined, pass-through (кроме фасадов IPC), лишних файлов-слоёв
- [ ] Вложенность ≤ 2, guard clauses (`let-else`, ранний `return`), нет долгоживущих `let mut` / `let`, исходы — значения
- [ ] Пустая строка после каждого оператора; одним блоком — только однотипные подряд
- [ ] Ветвления по данным — в чистых функциях или таблицах; у нетривиальных Rust-функций есть тест
- [ ] Rust: `unwrap` только для инвариантов, `let _ =` / `.ok()` с комментарием, замок не держится во время IO, `cfg` — в деталях
- [ ] React: эффект = ресурс + его очистка, производные данные без эффектов, нет вложенных тернарников, `.catch` не пустой без комментария
- [ ] Граница IPC: Rust-структура, `types/index.ts` и `tauriCommands.ts` согласованы; дублированная логика помечена с обеих сторон
- [ ] «Почему»-комментарии перенесены вместе с кодом
- [ ] Мёртвый код и лишние особые случаи удалены, изменения поведения перечислены; если видны пользователю — `CHANGELOG.md`, тексты — во всех 5 локалях
- [ ] `cargo check`, `cargo test`, `npx tsc --noEmit` проходят; метрики не хуже, в отрефакторенном — ноль; `cargo fmt` не запускался
- [ ] `docs/PLAN.md` и `docs/STATUS.md` обновлены
