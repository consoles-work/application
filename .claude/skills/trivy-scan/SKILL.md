# Проверка devconsole-hub через Trivy

Цель — не вывалить простыню CVE, а ответить на вопрос «что в приложении,
которое получат пользователи, уязвимо и что с этим делать», а затем сделать
это. Итог — markdown-отчёт с коротким списком действий сверху и подробностями
ниже, плюс журнал `docs/SECURITY_FIXES.md`. Сырые JSON сохраняются рядом,
чтобы к ним можно было вернуться без повторного скана.

Аргументы: `$ARGUMENTS` — сузить проверку (`rust`, `npm`, `docker`, `builder`).
Если пусто — fs-скан корня и config-скан `docker/`; образ сборщика — только если
он собран (см. ниже).

Все пути — от корня проекта.

## Что здесь проверять и насколько это важно

Это десктоп-приложение на Tauri 2, а не сервер: пользователю уходит бинарник
(`npm run tauri build`). Риск находки определяется тем, попадает ли пакет в
этот бинарник и обрабатывает ли он недоверенные данные.

| Что | Где | Попадает к пользователю | Чем чинить |
|---|---|---|---|
| Rust-крейты | `src-tauri/Cargo.lock` | да, вкомпилированы в бинарник | `cargo update -p <крейт>` / подъём версии в `Cargo.toml` |
| npm-пакеты фронта | `package-lock.json` | только `dependencies`, собранные Vite в `dist/` | `npm update <пакет>` / подъём в `package.json` |
| npm dev-зависимости | `package-lock.json` | нет (vite, tsc, tauri-cli — только на машине разработчика) | то же, приоритет ниже |
| Секреты | все файлы проекта | если они в git или в сборке | убрать из git, ротировать |
| Сборочный образ | `docker/Dockerfile.linux` → `devconsole-hub-linux-builder` | нет, только собирает Linux-пакеты | тег базы, `apt-get upgrade` |

Особенности, которые надо учитывать при разборе:

- **Trivy по умолчанию не показывает npm dev-зависимости** — так и надо: в
  сборку они не попадают. Флаг `--include-dev-deps` — только если просят
  аудит машины разработчика / supply chain.
- **`Cargo.lock` содержит крейты всех платформ** (windows-*, объекты для Linux
  GTK и т.д.). Находка в крейте, который на macOS не компилируется, всё равно
  важна для Windows/Linux-сборки — уточни платформу по `cargo tree -i <крейт>
  --target all` (из `src-tauri/`), прежде чем понижать приоритет.
- **Что в зоне атаки.** Недоверенные данные приходят из: вывода PTY/SSH
  (xterm.js, `portable-pty`), импортируемых `.dchub` (`export.rs`: aes-gcm,
  pbkdf2, serde), ответов AI-провайдеров (SSE, `reqwest`/fetch), содержимого
  wiki (TipTap, lowlight), файлов SSH-ключей и `~/.ssh/config` (`ssh-key`).
  Уязвимость в этих путях — выше; в коде, куда данные приходят только от
  самого пользователя (настройки, дерево), — ниже.
- **WebView — системный** (WKWebView на macOS, WebView2 на Windows, WebKitGTK
  на Linux) и в бинарник не входит; его CVE Trivy здесь не увидит и чинить их
  не нам.
- **Секрет-сканер найдёт `.env` / `src-tauri/.env`** с `DB_ENCRYPTION_KEY` —
  это ожидаемо. Проверь `git check-ignore -v <файл>` и `git log --all --
  <файл>`: если файл никогда не был в git — отметить и не требовать ротации.
  Если ключ был в истории — это первая строка «Что чинить»: ключ встроен в
  выпущенные бинарники (`build.rs`), ротация означает новый ключ БД, так что
  согласовать с владельцем (миграция существующих баз).
- **Исключения fs-скана обязательны**: `node_modules` (дублирует
  `package-lock.json`, сотни МБ), `src-tauri/target` (артефакты cargo, гигабайты),
  `dist`, `dist-linux`, `.git`. `site/` (лендинг) оставить — там могут быть секреты.
- **Образ сборщика** `devconsole-hub-linux-builder` (из `scripts/build-linux.sh`)
  сканировать, только если он есть локально (`docker images
  devconsole-hub-linux-builder`) или его явно просят. Его CVE не попадают к
  пользователям, но собранные в нём `.deb`/`.AppImage` линкуются с его
  библиотеками. Misconfig вроде «запуск от root» и `curl | bash` для
  одноразового сборщика — осознанно принятый риск, а не срочная задача.
- **История решений** — `docs/SECURITY_FIXES.md`. Если файла нет — создай при
  первом прогоне (сводка «было/стало», «Исправлено», «Принято», «План»). Если
  есть — прочитай до разбора: часть остатка уже разобрана и принята.

## 1. Запустить сканирование

```bash
SKILL=.claude/skills/trivy-scan
OUT=docs/security/trivy-$(date +%F)

"$SKILL/scripts/scan.sh" --out "$OUT/raw" \
  --fs . \
  --skip-dir node_modules --skip-dir src-tauri/target \
  --skip-dir dist --skip-dir dist-linux --skip-dir .git \
  --config docker
# + --image devconsole-hub-linux-builder, если образ собран
```

Trivy запускается как сервис `trivy` из `.claude/skills/trivy-scan/docker-compose.yml`
(`docker compose run --rm`): версия закреплена там (`TRIVY_VERSION`), корень
проекта монтируется в `/scan` только на чтение, результаты — в `/out`, база
уязвимостей — общий external volume `trivy-cache`, `docker.sock` — для скана
локальных образов. Поэтому `--fs`/`--config` должны лежать внутри проекта.
Нужен запущенный Docker Desktop; не запущен — скажи пользователю, не запускай
сам. Первый запуск качает образ и базу — несколько минут, таймаут Bash не меньше
600000 мс, предупреди пользователя. Скан образа сборщика — около 2 минут.

Версию Trivy поднимать осознанно (правка `docker-compose.yml` + отметка в
журнале): новые правила меняют счётчики, и «было/стало» перестаёт сравниваться.

Флаги:
- по умолчанию — все находки; в отчёте построчно расписаны только
  critical/high с исправлением, нечинимые сгруппированы по пакетам;
- `--fixed-only` — только с исправлением (`--ignore-unfixed`);
- `--offline` — не обновлять базу.

Упавший скан одной цели не останавливает остальные: собери отчёт по тому, что
есть, и напиши, какая цель не проверена и почему.

Для Rust можно сверить с `cargo audit` (база RustSec, видит и
`unmaintained`/`yanked`, которых нет у Trivy) — если `cargo-audit` установлен:
`cd src-tauri && cargo audit`. Не установлен — упомяни в отчёте, не ставь сам.

## 2. Собрать отчёт

```bash
python3 "$SKILL/scripts/report.py" --in "$OUT/raw" --out "$OUT/report.md" \
  --title "Отчёт Trivy: devconsole-hub"
```

`raw/` в `.gitignore` (JSON образа — десятки МБ); в git идёт `report.md`.

В таблицах находок колонка «Файл» показывает lock-файл — по ней видно, Rust это
или npm.

## 3. Дописать «Что чинить в первую очередь»

Замени комментарий-заглушку в `report.md` на 3–6 пунктов:

- **Действие, а не CVE.** «`cargo update -p rustls` → 0.23.x закроет 3 находки,
  из них 1 critical», а не «CVE-2024-XXXX в rustls».
- **Сгруппировано по причине** — один `cargo update` часто закрывает несколько
  находок сразу; см. «Пакеты с наибольшим числом находок».
- **По риску, а не по количеству** (таблица и «зона атаки» выше): секреты в
  git — в самый верх; затем Rust-крейты и npm `dependencies` на путях с
  недоверенными данными; затем остальное в бинарнике; dev-зависимости и
  образ сборщика — в конце.
- **Транзитивная зависимость** — назови, через что она тянется
  (`cargo tree -i <крейт>`, `npm ls <пакет>`): если фикс требует подъёма
  `tauri`/плагина, это отдельная задача с проверкой приложения.
- **Честно про нечинимое** — ждать фикса, заменить пакет или принять риск;
  если риск уже принят в `SECURITY_FIXES.md`, сошлись на пункт.

## 4. Устранить

Чинить то, что закрывается на нашей стороне, согласовав с пользователем объём:

- Rust — из `src-tauri/`: `cargo update -p <крейт>` (в пределах semver из
  `Cargo.toml`) или `cargo update -p <крейт> --precise <версия>`; если нужен
  выход за диапазон — правка `Cargo.toml`. Не трогать версию приложения в
  `Cargo.toml` — её пишет `scripts/version.mjs`;
- npm — `npm update <пакет>`; для транзитивных — подъём родителя или
  `overrides` в `package.json`. `npm audit fix --force` не запускать — он
  поднимает мажорные версии без спроса;
- сборщик — правка `docker/Dockerfile.linux` (тег базы `ubuntu:22.04` →
  новее LTS, Node 20 → актуальная LTS), повторная сборка `scripts/build-linux.sh`
  только с согласия владельца — она долгая.

После любого исправления зависимостей:

```bash
cd src-tauri && cargo test && cd ..   # Rust: компиляция + тесты
npx tsc --noEmit && npm run build     # фронт
```

Подняли `tauri`, плагин или крейт из «зоны атаки» — попроси владельца
прогнать `npm run tauri dev` и проверить затронутое (терминал/SSH, импорт
`.dchub`, AI-чат, wiki). Что не прогнано — назвать в отчёте.

По `docs/RULES.md`: до правок — пункт в `docs/PLAN.md`, после — `PLAN.md`,
`docs/STATUS.md` и строка в `CHANGELOG.md` → «Не выпущено» → «Исправлено»
(обновление зависимостей видно пользователю как исправление уязвимости).
Версию не поднимать — это решение владельца.

Коммиты не делать — изменения остаются в рабочем дереве.

## 5. Обновить журнал и отдать результат

- В `docs/SECURITY_FIXES.md`: дату прогона, строки сводки «было/стало», новые
  пункты «Исправлено» (что и почему), «Принято» (с причиной), обновить «План».
- В чат — 5–10 строк: счётчики по уровням (и было/стало, если есть прошлый
  отчёт в `docs/security/`), отдельно Rust / npm / сборщик, что исправлено,
  что осталось, путь к отчёту. Полные таблицы CVE в чат не копировать.
- Если отчёт за сегодня уже существует — не перетирать молча, показать разницу.
